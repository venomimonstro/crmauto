# Комплексный аудит и программа коммерческой приёмки CRM Auto
**Дата:** 2026-10-19. **Статус:** NO-GO. **Источник:** код ветки main, ручная проверка маршрутов API/React и добавленные тесты.

## Важная граница достоверности
Фактический браузерный E2E, Django/DRF, миграции PostgreSQL, нагрузка, реальные переводы денежных средств, ККТ, SMTP, восстановление резервных копий и работа развёрнутого SaaS из текущего окружения **не запускались**. Наличие файла тестов не равно прохождению тестов. Отсутствуют зависимости Django и доступ к БД / работоспособному хостингу. Симуляция — маршруты сквозных API-тестов и ревью кода; до прогона их статус «НЕ ПРОВЕРЕНО».

## Сценарий A — покупатель подписки (владелец нового СТО)
1. Узнать тарифы: публичный GET /api/v1/billing/plans — реализован.
2. Зарегистрировать безопасную учётную запись: реализованы opt-in письмо подтверждения, ввод исходного пароля, токен и восстановление доступа. Пока SMTP не подключён и ENABLE_EMAIL_ONBOARDING=0, самостоятельная регистрация **отключена** — P0.
3. После подтверждения email войти: API логина есть; тестовые сценарии добавлены, но SMTP и браузер не проверены.
4. Создать компанию: создаётся один основной филиал и **14-дневный trial** из серверно созданного плана — код реализован. Повторное бесплатное создание другой организации ограничено.
5. Настроить услуги, персонал, филиалы: часть функций отсутствует. В стартовом trial: максимум один филиал и три сотрудника (ограничение трёх сотрудников пока НЕ обеспечено API, потому что сценарий приглашения персонала отсутствует).
6. Оплатить подписку: платёжный провайдер, проверенные webhooks, автопродление отсутствуют — P0.
7. После истечения: GET сохраняется, POST/PATCH блокируются при BILLING_ENFORCE_WRITES=1 — реализовано под безопасным флагом. На текущем production неизвестно, установлен ли этот флаг.
8. Безопасно восстановить работу: операторское продление и банковская сверка не реализованы — P0.

## Сценарий B — владелец действующего автосервиса
1. Завести клиента, автомобиль, связать собственника → код есть.
2. Записать на пост и проверить конфликт записи → код есть; календарь, переносы и рабочие часы неполны.
3. Отметить прибытие, создать визит, заказ-наряд → API есть.
4. Заполнить смету, отправить на согласование, получить согласование → сотрудник может указать reference; **подтверждение клиента не доказано** — P0.
5. Начать ремонт, резервировать и списать детали → код есть, но себестоимость, партии и реальный акт расхода неполны — P0.
6. Сформировать начисление и получить наличные → внутренний кассовый журнал и экран есть; незаверенные card/bank запрещены на сервере.
7. Выписать чек, подтвердить фискализацию, выдать машину, закрыть визит → связанный контур не завершён — P0.
8. Посчитать прибыль → полноценные затраты отсутствуют, чистая прибыль сознательно не вычисляется — P0.

**Автоматизированный контракт:** backend/core/test_owner_journey.py проходит этот маршрут через API вплоть до начисления, частичной оплаты и защиты от переплаты (ФАЙЛ ТЕСТА ДОБАВЛЕН; не подтверждено фактическое выполнение).

## Сценарий C — автовладелец как клиент СТО
Получить проверенный PortalGrant → увидеть свои автомобили и ремонты → увидеть опубликованную смету.
Фильтр доступных заказов усилен точной связкой user/customer/organization через Exists; MyPortal запрещает несогласованную связку customer.organization.
Подтверждённая регистрация, подписание сметы, онлайн-запись, сообщения и удобный самостоятельный ЛК клиента НЕ завершены — P0.

## Исправления текущего аудита
- Утечка ответа чужой идемпотентной команды: отказ, если ключ привязан к другому пользователю.
- Платформенное ограничение записи: общий guard на TenantAPIView + проверка активности и срока Subscription; переключатель BILLING_ENFORCE_WRITES для безопасной миграции существующих клиентов.
- Trial-онбординг: дата завершения и план из миграции, ограничение повторного создания, ограничение филиалов с блокировкой Organization для конкурентности.
- Запрет принимать неподтверждённые card/bank-платежи как фактические денежные движения.
- Защита общего поиска CRM правами доступа.
- Межарендная проверка клиентского портала.
- Веб-экран внутреннего учёта наличных, начислений, задолженности и возвратов.
- Тестовые контракты для сценария нового покупателя, владельца СТО, проверки идемпотентности, регистрации и восстановления с одноразовыми ссылками.
- Страница входа с регистрацией, подтверждением и сбросом пароля (feature flag + SMTP необходимы).
- Отдельный staging-контейнер Nginx/React и compose.production.yaml, который требует воспроизводимый package-lock.json.

## Контроль выпуска
Скрипт scripts/commercial_acceptance.sh предназначен **только для одноразового staging**, требует CONFIRM_DISPOSABLE_STAGING=YES. Он проверяет синтаксис Python, Django deployment checks, непротиворечивость миграций, тесты нескольких доменов, frontend build и release_preflight.
Команда release_preflight специально продолжает блокировать допуск к production без доказанного PSP/ККТ и восстановления. Статус GO возможен только после подписания результатов ручного E2E, security pentest, restore drill и устранения всех P0.
