# CRM Auto — комплексная стабилизация интерфейса и боевой релиз
**Дата:** 2026-10-19. **Состояние:** NO-GO для продажи и боевого финансового учёта.

## Исправления этого прохода
1. Главная владельца: живые запросы к /api/v1/reports/daily с фильтром по филиалу, явными loading/error/retry, переходами к задачам и реальными денежными суммами с копейками.
2. Старые заглушки в главном экране для владельцев и управляющих удалены. Для остальных сотрудников предусмотрено простое рабочее меню по допустимой роли.
3. Навигация скрывает разделы, к которым у роли нет доступа. Смена компании инвалидирует запросы клиентов/автомобилей по номеру поколения и не показывает ответы предыдущего tenant.
4. Шиномонтаж: самостоятельный экран регистрации, поиска и выдачи комплектов. В API появился инвариант, что указанный автомобиль имеет действующего владельца, равного выбранному клиенту. Клиентские шины никогда не попадают в товарные остатки.
5. Отчёты игнорируют старые ответы при смене филиала. После возврата средств неоплаченные начисления снова показываются как долг.
6. Исправлена проверка времени в форме записи, чтобы ошибка даты не оставляла кнопку в состоянии выполнения.
7. Ошибки DRF-полей отображаются в форме; при сетевом сбое указана неопределённость факта выполнения.
8. Касса не помечает запись как неудачную, если успешное POST сопровождалось неудачной загрузкой списка. Изменения денег в CRM не являются подтверждённым фискальным чеком.
9. Адаптивность, клавиатурный фокус и системные шрифты без внешней зависимости.
10. Коммерческий сценарий staging останавливается перед миграциями при отсутствии package-lock.json, и на строго одноразовой базе применяет миграции перед тестами.

## Проверки по ролям и UI (НЕ ВЫПОЛНЕНЫ на реальном стенде)
- Владелец: новая компания → trial → основные разделы → живой dashboard, ошибки сети, смена филиалов, права на персонал.
- Управляющий: задачи, касса, склад, филиалы; проверка ограничений.
- Приёмщик: запись → визит → заказ-наряд, дополнительные дефекты, шины клиента; не видит чужие компании.
- Механик: только доступные ему операции и задания, без персональных данных владельцев сверх необходимого.
- Кладовщик: склад и авторазбор; не может проводить оплату или менять клиента.
- Кассир: касса, без общего поиска клиентов и машин.
- Наблюдатель: отсутствие кнопок записи/изменения; запросы POST всё равно должны отклоняться на сервере.
- Клиентский портал: владелец одной машины не открывает чужую смету по UUID.
- Мобильный экран 320/375/768 px: боковое меню, фокус с клавиатуры, длинные таблицы, формы, прокрутка.
- Медленная сеть/двойной POST: проверка таймаутов, повторных ключей, невозможности дублировать кассовые операции.

## Запрет на GO и точные блокеры
**P0-1**. Нет воспроизводимого `frontend/package-lock.json`. Получить его на машине с разрешённым npm registry: в `frontend` запустить `npm install --package-lock-only --ignore-scripts`, затем `npm ci --no-audit --no-fund` и `npm run build`. Закоммитить проверенный lockfile в main вручную. Не переключать Dockerfile на небезопасный npm install на боевом сервере.
**P0-2**. Не проведены настоящие миграции, тесты и браузерные прогоны на изолированном PostgreSQL/Redis. Скрипт `scripts/commercial_acceptance.sh` только для disposable staging, требуется `CONFIRM_DISPOSABLE_STAGING=YES`; без такого подтверждения запуск запрещён.
**P0-3**. Этапы согласования дополнительных работ клиентом, связанной себестоимости складских партий, выдачи авто, кассовой/банковской сверки, чека/ККТ и гарантии не доведены до подтверждённого end-to-end.
**P0-4**. Нет доказанного восстановления из резервной копии, проверенных SMTP/TLS, административной MFA и пентеста.
**P0-5**. Коммерческая оплата SaaS/автопродление требуют реального PSP с криптографически проверенными уведомлениями. Тестовых моделей недостаточно.

## Условия коммерческого допуска
- 0 известных P0, зелёные скрипт приёмки и полноценный браузерный E2E;
- нет IDOR/межарендной утечки при 2+ организациях в одной учётной записи;
- оплата, возврат, чек, закрытие и гарантия подтверждены на реальных интеграциях;
- нагрузки на бронирование, склад и деньги испытаны в параллельных запросах;
- проведена восстановительная тренировка, результаты задокументированы.
